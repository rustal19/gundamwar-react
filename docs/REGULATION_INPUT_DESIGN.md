# レギュレーション入力の構造化(#18)+ プール指定(#19)

起案: 2026-08-26(司令塔)。関連: [FEEDBACK_BACKLOG.md](FEEDBACK_BACKLOG.md) #18 / #19、
[DECK_STATE_DESIGN.md](DECK_STATE_DESIGN.md)(提出デッキの検証と地続き)。

## 1. 現状(調査結果)

### 1.1 保持形式は既に構造化されている

`regulation` は次の形で、フォーマットプリセット(`src/data/*.json`)では
**禁止/制限がカードIDの配列**で入っている。

```
regulation: {
  name, mainMin, mainMax, sideSize, maxCopies,
  allowedSets: string[]|null,   // 収録弾の日本語名
  bannedCards: string[],        // 例: "101020126"(カードID)
  limitedCards: string[],
}
```

### 1.2 問題は「入力」と「照合の甘さ」

- 主催者の大会作成フォーム(`src/pages/TournamentManage.js`)は
  `bannedCardsText` / `limitedCardsText` / `allowedSetsText` という**自由テキスト**で、
  `textToList` で改行/カンマ区切りにするだけ。**何を入れても通る**。
- 照合(`src/utils/deckValidation.js` の `matchesCardRef`)は
  **「カードID または カード名の完全一致」**。つまり打ち間違い・表記ゆれ・略称は当たらず、
  **禁止カードを指定したつもりで何も禁止されていない**状態が黙って成立する。
- `allowedSets` も同じく自由テキストで、収録弾名が1文字違えばプール制限が効かない。

**#18 の本質は「自由記載を禁止する」ことではなく、「入力を必ずカード/弾に解決させ、
解決できないものを保存させない」こと。** 保持形式は変えなくてよい。

## 2. 方針

1. **保持形式(§1.1)と `validateDeck` は変えない**。既存プリセット・既存大会と互換を保つ。
2. 入力を**カード検索で選ぶ形式**にし、保存値は**カードIDに統一**する。
3. 一括貼り付けは許すが、**1行ずつ解決**し、解決できない行が残っている間は保存させない。
4. 既存データ(名前で入っている可能性がある)は**読み込み時に壊さない**。
   保存時に解決を試み、解決できないものは警告付きで残す(遡及的に消さない)。

## 3. 禁止/制限カードの入力(#18)

- 入力欄はカード検索。既存のカード検索(`/api/search`)を使い、候補から選んで追加する。
  **カードIDでの逆引きができるか**は要調査(できない場合はカード名検索→候補提示で代替)。
- 追加済みは「カード名(ID)」のチップで表示し、個別に削除できる。
- **一括貼り付け**: 改行区切りで名前/IDを流し込める。行ごとに解決し、
  - 一意に解決 → チップ化
  - 複数候補 → 候補から選ばせる
  - 解決不能 → 「未解決」として赤字で残す
- **未解決が1件でもあると保存不可**(これが「自由記載不可」の実装)。
- 保存値はカードIDの配列。表示用の名前は保存しない(カード名は都度引く)。

## 4. プール(使用可能セット)の指定(#19)

2つのモードを用意し、**保存形は従来どおり「収録弾の日本語名の配列」**に展開する
(`validateDeck` を変えないため)。

- **弾選択モード**: `src/data/searchOptions.js` の `SET_INCLUDED_OPTIONS` ほかから複数選択。
- **弾カットオフモード**: 「この弾まで」を1つ選ぶと、その弾までの全弾を選択状態にする。
  ※ 当初は「日付カットオフ」を想定したが、**弾ごとの発売日テーブルは存在しない**
  (`DECK_RANGE_PRESET_CUTOFFS` / `TENSAKU_OPTIONS` は定義だけで未使用の名残、
  親リポジトリの `csv/card_set_inclusion.csv` にも発売日は無い)。
  一方で同CSVの列は**発売順**に並んでおり、`SET_INCLUDED_OPTIONS` も同じ順序を保っている。
  そのため「日付」ではなく「弾の並び順」でカットオフする。結果として得られるプールは同じで、
  持っていない発売日データを作らずに済む。

- 「制限なし(全カード)」は `allowedSets: null` のまま。

## 5. 表示側への波及

- 大会詳細のレギュレーション表示は、禁止/制限を**カード名で**出す(現在はIDが出ている可能性)。
- デッキ構築・検索の禁止/制限バッジ(#32 で実装済み)は保存形が変わらないのでそのまま動く。

## 6. 前提データ: 収録弾の並び順(調査済み)

弾カットオフ(#19)には「弾の発売順」が要る。これは既にある:
親リポジトリ `csv/card_set_inclusion.csv` の列順(1st, 2nd, DS1_1, ... 28th, PR, BG, joke)が
発売順で、アプリ側の `src/data/searchOptions.js` の弾オプションも同じ順序を保っている。
**新規データの用意は不要**。実装時は「searchOptions の並び順が発売順である」ことを
コメントで明示し、順序に依存していることが分かるようにする。

## 8. 決めておくこと

- **未解決行があるときは保存不可**(§3)で進める。警告だけにすると #18 の意味がなくなるため。
- 既存大会の既存データは遡及的に書き換えない(§2-4)。
- カード名の完全一致による照合(`matchesCardRef`)は**残す**。既存プリセットに名前で
  入っているものがあり得るため、IDのみに絞ると既存の禁止指定が外れる危険がある。
